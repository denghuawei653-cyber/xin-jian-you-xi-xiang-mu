# Godot 场景冲突处理手册

`.tscn` / `.tres` 是纯文本文件，Git 能把它们合并成"没有冲突标记"的状态，
但结果**经常是打不开或者节点错乱**。这个文件讲怎么处理。

---

## 一、先判断：这次冲突有多严重

```bash
git status                       # 看哪些文件冲突了
git diff --name-only --diff-filter=U
```

分三种情况：

| 情况 | 表现 | 处理方式 |
| --- | --- | --- |
| **A. 不同区域** | 两人改的是场景里不同节点，冲突标记很干净 | 可以手工合并，见第二节 |
| **B. 同一节点** | 冲突段落指向同 `[node name="X"]` | 必须沟通，见第三节 |
| **C. 大范围冲突** | 几十上百行冲突，或含 `[sub_resource]` | 不要硬解，见第四节 |

---

## 二、情况 A：不同区域的干净冲突

```bash
# 1. 先看一眼冲突范围
git diff scenes/level_01.tscn

# 2. 用带三方视图的工具打开（推荐 VS Code + GitLens，或 meld）
git mergetool scenes/level_01.tscn

# 3. 合并后务必验证：用 Godot 打开该场景，肉眼确认节点树完整
#    然后运行一次场景，确认没有 "Node not found" 之类的报错
```

`.tscn` 的结构是「头部 `[ext_resource]` / `[sub_resource]` 列表 + 若干 `[node]` 段」。
**同一个节点的段落必须整体保留一份**，不能把两个版本的字段拼起来——这是最常见的解错方式。

注意 `[ext_resource]` 的 `id="1_abcde"` 这类编号：两份改动各自新增资源时，
编号可能撞车，必须手动改成不重复的值，并同步更新引用它的节点属性。

---

## 三、情况 B：两个人改了同一个节点

**不要试图在文本上合并。** 正确做法：

1. 在群里找到另一个人，问清楚各自改了什么。
2. 决定谁的版本为基准。
3. **你的版本回滚，重新在对方的最新场景上改一遍。**
   用编辑器重做一遍通常只要几分钟，比解冲突快，而且不会留下半坏的场景。

```bash
# 放弃自己对这一场景的修改，换成对方的最新版
git checkout --theirs scenes/level_01.tscn
# 或者干脆从头来
git checkout origin/develop -- scenes/level_01.tscn
```

---

## 四、情况 C：大范围冲突，或者已经解坏了

最省时间的路是「**保基准，重做你的改动**」，而不是在烂摊子里继续挖：

```bash
# 1. 停掉当前合并
git merge --abort          # 如果是 merge
# 或 git rebase --abort    # 如果是 rebase

# 2. 备份你的场景，留个后路
cp scenes/level_01.tscn /tmp/level_01.myversion.tscn

# 3. 让本地场景回到对方的主干版本
git fetch origin
git checkout origin/develop -- scenes/level_01.tscn

# 4. 用 Godot 打开，把你在备份版本里做的改动重做一遍
#    （可以两个 Godot 实例并排开，对照着改）
```

**重做不一定比重解慢，但一定更可靠。**

---

## 五、验证合并结果（必做）

无论用哪种方式解完冲突，合并提交之前必须：

1. 用 Godot 打开项目，确认编辑器里**没有报错弹窗**。
2. 打开被合并的场景，检查节点树结构和属性面板是否符合预期。
3. 实际运行一次该场景，看有没有 `Node not found` / `Invalid get index` 之类的运行时报错。
4. 用 `git diff --cached` 再看一眼最终要提交的内容，确认没有残留的
   `<<<<<<<` / `=======` / `>>>>>>>` 标记：
   ```bash
   git diff --check
   ```

只有四步都过了，才 `git commit` 完成合并。

---

## 六、以后怎么避免

这不是"运气不好"，基本都是流程问题：

- **拆场景。** 一个场景超过 15 个节点就该考虑拆成子场景实例化。
  玩家、敌人、道具、UI 元素各自独立成 `.tscn`，冲突面积直接降一个数量级。
- **明确负责人。** 同一个场景同一时间只安排一个人改。
- **批量改动写成脚本。** 要给 200 个节点加同一段元数据？写个 EditorScript 跑，
  而不是手工点。结果作为一次干净提交，别人也好 review。
- **及时 rebase。** 分支放三天不合，冲突面积就会翻倍。
- **`Main.tscn` 保持极薄。** 它应该只是几个子场景的容器，不应该有具体逻辑。

---

## 七、拉取资源后画面不对？

多半不是冲突，而是：

1. **LFS 没拉全** → `git lfs pull`
2. **`.import` 文件没跟着提交** → 检查 `git status`，导入参数文件必须入库
3. **Godot 版本不一致** → 版本不同会重新导入，参数被改写
4. **本机缓存过期** → 关掉 Godot，删掉本地 `.godot/` 目录（这个是安全的，
   Godot 会重新生成），再打开
